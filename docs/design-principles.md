# 设计原则

这份文档解释“为什么是这个样子”。改 UI 之前先读一遍，能避免把工作台做成又一个后台首页。

## 一句话

**工作台是一张可以反复回来的工作台面，不是产品官网、数据大屏或内容管理系统。**

它的第一屏应该直接是“我现在要处理的条目”，而不是欢迎语、指标卡或功能入口。

## 7 个界面部件 + 2 层地基

| # | 部件 | 职责 | 不应该做什么 |
| --- | --- | --- | --- |
| 1 | 顶栏 | 品牌、搜索、刷新（dialog 宿主可多一个关闭） | 不放导航菜单、通知中心、头像 |
| 2 | 模式 Tab | 切换“今天怎么工作” | 不按内容分类加 Tab |
| 3 | 筛选条 | 两行 chip + 状态/时间/条数 | 不做弹层、不做左树 |
| 4 | 列表 | 全宽、行式、可扫读 | 不做卡片网格、不做瀑布流 |
| 5 | 详情 | 阅读标题、元数据、摘要、原文 | 不堆操作按钮和统计 |
| 6 | 编辑区 | 只编辑摘要/判断/状态 | 不编辑原文，不做富文本编辑器 |
| 7 | 动作条 | 编辑/保存/分析/放入对话/发送 | 不藏进“更多”菜单 |
|  | 数据层 | index / annotations / content / reports | 不把状态写进原文 |
|  | 宿主层 | 文件、会话、剪贴板、窗口 | 不让 UI 直接依赖某个宿主 SDK |

## 布局

```text
┌──────────────────────────────────────────────────────────┐
│ 品牌   搜索…………………………………  /        刷新            │  顶栏
├──────────────────────────────────────────────────────────┤
│ 今日    资料库    报告    设置                            │  模式 Tab
├──────────────────────────────────────────────────────────┤
│ 层级  全部  示例市  示例省  示例区  示例部门              │  筛选行 1
│ 类型  全部  原文  解读  数据  申报 …   状态▾ 时间▾ 共 10 条│  筛选行 2
├──────────────────────────────────────────────────────────┤
│ 日期   层级  类型  标题 / 摘要                  状态  机构 │  列表头
│ 11-12  示例市 原文 智能终端产业发展行动方案…   待研判  …   │  行 46px
│ 11-10  示例市 申报 智能制造试点项目申报…       在跟    …   │
│ …                                                        │
├──────────────────────────────────────────────────────────┤
│ 已读取 10 条 · 2 份报告              10 条 · 2 份 · web   │  底栏
└──────────────────────────────────────────────────────────┘
```

详情页替换中间区域；筛选条隐藏，动作条吸底。不要用弹窗承载详情，也不要在右侧再开一列。

## Tab 是模式，不是内容分类

这是最容易做错的一条。

| Tab | 回答的问题 | 数据范围 |
| --- | --- | --- |
| 今日 | 今天先看什么？ | 最近 N 天 + 待处理 + 临近截止 |
| 资料库 | 全部东西在哪？ | 全量条目 |
| 报告 | 我产出了什么？ | 报告列表 |
| 设置 | 系统现在什么状态？ | 配置、宿主、快捷键 |

判断方法：**如果新增一个 Tab 只是为了让某一类内容有地方放，那它应该是 chip，不是 Tab。**

- “竞品”“申报”“解读”是类型 → 第二行 chip。
- “国家/省/市/区”是层级 → 第一行 chip。
- “本周/本月/归档”是时间或状态 → 右侧下拉。
- “复盘”如果是一种不同的工作方式（只看已完成、按结论聚合）→ 才可以考虑新 Tab。

Tab 数量控制在 3–5 个。超过 5 个，先问是不是把分类误当成了模式。

## chip 是筛选，不是导航

- 点击 chip 只缩小当前列表，不跳页、不重载、不改变 Tab。
- 两个维度的 chip 是 **AND** 关系；同一维度内是单选（“全部”= 清除该维度）。
- 状态、时间是额外的 AND 条件；搜索也是 AND。
- 右侧实时显示“共 N 条”，让用户知道筛选有没有生效。
- 窄栏不换行：两行各自 `overflow-x: auto`，隐藏滚动条，手指/触控板横向滑动。不要为了放下所有 chip 而缩小字号或换行成三行。
- 选中的 chip 必须有明显的背景/边框/字重变化，不能只靠颜色细微差别。
- 清空筛选是一个显式动作；空状态里给“清空筛选”按钮。

反例：把 chip 做成下拉菜单、把筛选项放进抽屉、点击 chip 后弹出一个新页面。这些都会让“比较和组合”变慢。

## 内容优先

- 列表以“行”为单位，不以“卡片”为单位。行高 44–50px，一屏能扫 12–18 条。
- 标题一行，摘要一行；不要每行都放标签墙、进度条、头像。
- 详情先给标题和 3–6 个元数据 chip，再给摘要，再给原文。不要先放统计卡。
- 不在首屏放 hero、插画、功能介绍、使用教程。教程放 `docs/`，不占工作区。
- 不用大面积阴影、渐变、玻璃拟态。一个暖色强调色足够。
- 数字用等宽字体，日期用 `YYYY-MM-DD`，状态用短标签。

## 阅读与编辑分离

阅读态和编辑态是两个明确的状态，不要“看起来像正文、点一下就能改”。

- 阅读态：摘要和判断渲染 Markdown；原文只读；动作条显示“编辑”。
- 编辑态：摘要和判断变成 textarea；状态变成 select；动作条显示“取消/保存”。
- 原文 `content.md` **永远不写**。编辑只写 `annotations.json`。
- 保存失败时保留编辑态和草稿，不要假装成功。
- `Esc` 取消编辑，`Ctrl/Cmd+S` 保存。

为什么：原文是证据，批注是你的判断。混在一起，三个月后你分不清哪句是文件说的、哪句是你猜的。

## 全宽列表，不要左树

窄栏（侧栏 360–480px）里，左树会吃掉 40% 的宽度，剩下的标题只能显示 8 个字。横向 chip 只占两行高度，把宽度全部留给内容。

- 列表占满内容区；详情页替换列表，不并排。
- 不在列表左侧放层级树、文件夹树、标签树。
- 需要层级时，用第一行 chip；需要分类时，用第二行 chip。
- 条目超过 200 条再考虑虚拟滚动；10–200 条直接渲染。

## 不要“更多”，不要营销页

- 每个条目都能点开详情；不要把关键动作塞进 `⋯` 菜单。
- 详情底部动作条固定 5 个：编辑、保存、让 Agent 分析、放入对话、发送。窄栏横向滚动，不换行、不折叠。
- 没有“查看更多”“加载更多”“进入专区”。列表就是全部；筛选就是缩小。
- 第一屏不是 landing page。没有“欢迎使用”“开始探索”“产品能力”三栏。

## 视觉基线

| 项目 | 值 | 原因 |
| --- | --- | --- |
| 正文 | 13.5px / 1.7 | 侧栏密度和可读性的平衡 |
| 列表行高 | 桌面 46px（44–50） | 一屏 12–18 条；窄栏两行标题可更高 |
| 圆角 | 4–6px | 克制，不玩具化 |
| 强调色 | 一个暖色（默认陶土色） | 选中、链接、主按钮共用 |
| 背景 | 浅中性暖灰 | 比纯白柔和，长时间阅读不刺眼 |
| 边框 | 1px 低对比 | 用线分隔，不用阴影 |
| 断点 | 420 / 760 / 1000 | 手机、窄侧栏、宽面板 |
| 420px | 不横向溢出 | 搜索、Tab、筛选、动作条各自横向滚动 |

状态色只用于状态徽标（待研判/在跟/已研判/已归档），不要扩散到整行背景。

## 键盘

| 键 | 行为 |
| --- | --- |
| `/` | 聚焦搜索；输入框内不触发 |
| `Esc` | 清空搜索 → 取消编辑 → 返回列表 → 清空筛选 |
| `Ctrl/Cmd + S` | 保存当前批注；不在编辑态时忽略 |
| `Tab` | 正常焦点顺序；所有 chip/按钮可键盘操作 |

焦点可见：`:focus-visible` 用强调色描边，不要 `outline: none` 了事。

## 自查

改完问自己：

1. 第一屏是不是直接能看到条目？
2. 新增的东西是“模式”还是“分类”？如果是分类，为什么不是 chip？
3. 两个筛选维度能组合吗？组合后条数变了吗？
4. 420px 宽会不会横向溢出？筛选条和动作条是不是各自滚动？
5. 阅读态和编辑态是否一眼能区分？
6. 保存后刷新，批注还在吗？原文有没有被改？
7. 没有聊天宿主时，分析/发送有没有明确降级提示？
